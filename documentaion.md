AI Resume Builder Project Documentation

Author: Abdul Mujahid
Program: B.S. Computer Science, MSU Denver (A.S. Computer Science, CCA)
Status: Draft v0.1

The AI Resume Builder is a web-based application that helps learners convert their unorganized background in terms of education, projects, work experience, and skills into an ATS-friendly resume. The work is done using an AI model to write and phrase the resume, which is written using a professional LaTeX template. The basic concept operates in four processes. A student first provides his/her information in a simple form or a chat interface. Second, an AI model, Grok as the primary and Gemini as fallback, rewrites and arranges that information into strong, ATS-optimized resume bullet points and sections. Third, the content is pasted into a LaTeX resume template based on the ATS-Friendly Technical Resume template on Overleaf. Fourth, the system compiles the LaTeX into a PDF which the student is able to download.

A few recurring problems come up among most students, particularly those with little writing or HR experience, or CS students. They find it difficult to transform raw experience, such as "I made a to-do list app in React," into something that can go on a resume, such as "Developed a full-stack task management application using React and Node.js, cutting down the time spent manually tracking tasks by X%." They also have trouble creating a resume that gets past Applicant Tracking Systems, and they cannot create a clean, professional resume layout without wrestling with Word or Canva. AI Resume Builder addresses this by combining AI-created content with a pre-built, ATS-safe LaTeX template, so that the student just needs to submit raw facts.

It begins with Google Sign-In, enabling students to log in without managing a password, which is also the same pattern as Mohammad's AI Student Helper project. Here, students complete a resume intake form, which can be either a structured form or a guided chat, to gather their contact information, education, experience, projects, skills, and certifications. That raw input is passed through AI-generated content: Grok runs initially and reformats the input into robust, measurable, ATS-friendly bullet points, and in case of failure by Grok or a rate limit, the system will automatically give way to Gemini. The output is inserted into the placeholders of the ATS-friendly LaTeX template via a LaTeX template engine, and compiled into a downloadable PDF via a LaTeX engine like pdflatex or tectonic, or a hosted LaTeX compile API. The application maintains a history of resumes and stores past versions and drafts by user, allowing them to revisit or reuse a resume for a new job application, and supports edit and regenerate, allowing a student to edit any AI-created bullet or ask the AI to rephrase it or make it more technical. The ATS keyword matching, as a stretch feature, would allow a student to paste a job description, and missing keywords relevant to that job description would be highlighted or added by the AI.

The suggested stack has the same general structure as the reference project, but modified for this use case. On the front end, it is composed of HTML5, CSS3, and vanilla JavaScript, and Jinja2 templates in case you are using Flask to render pages. It is based on Python and Flask on the back end, with Flask-Session to handle session and state. For the database, it relies on PostgreSQL, hosted on something like Neon, with Flask-SQLAlchemy as the ORM. Authentication is done using Google OAuth 2.0 via Flask-Dance. The Grok API is the primary model used to generate the resume content through AI integration; an automatic and silent fallback to generate the resume content is provided by the Google Gemini API in case Grok is rate-limited or unavailable. Document generation is based on the ATS-Friendly Technical Resume LaTeX template on Overleaf, which needs compiling either with pdflatex or tectonic (when self-hosted) or with a hosted compile API (when you would rather not run a LaTeX install on the server). It would be deployed on Render or similar, using Gunicorn with automatic deployments from GitHub. This is similar to Mohammad's ai-student-helper stack, which makes a good starting point because you already have a working reference implementation of the OAuth and dual-AI-fallback components. You would primarily be replacing "answering a question" with "generating resume content," and adding the LaTeX and PDF pipeline on top.

The flow begins with the browser: the student fills out the intake form, and the information is transmitted to the Flask backend. The backend constructs a prompt based on that data and submits it to Grok. In case Grok fails, the backend retries with Gemini quietly, using the same fallback logic as the reference project. The AI response comes back as structured JSON with sections and bullet points, and it is processed by the backend. The resulting parsed content is then injected into the LaTeX template, replacing the template's placeholders, and then the LaTeX file is compiled into a PDF. Lastly, a PDF is returned to the student as a downloadable link, and the draft is saved to their history. Under the hood, the Flask app communicates with three components: the Grok API, which is the main AI; the Gemini API, which is the fallback AI; and a PostgreSQL database, where the user data, resume drafts, and history are stored, alongside the LaTeX engine, which fills the template and compiles the PDF.

For the prompting strategy, the AI must be asked to return structured output in JSON instead of plain text, so the result can be reliably mapped into LaTeX fields. A reasonable shape includes a summary string, an education array with school, degree, dates, and GPA, an experience array with title, company, dates, and bullets, a projects array with name, tech, and bullets, and a flat skills array. The system prompt must enforce ATS best practices: no graphics or tables in text sections, bullets that are action-verb-led, impact quantified where practical, no use of first-person pronouns, and sections written in short lines. A fallback chain of more than two models, Grok to Gemini and possibly to a third, free model, would not be a bad thing to have, patterned after the fallback setup of the Kimi and Nvidia API keys used by the reference repo.

The User table holds id, google_id, email, first_name, last_name, and created_at. The Resume table contains id, a user_id foreign key, title, an optional job_target field used for keyword matching, created_at, and updated_at. The ResumeVersion table contains id, a resume_id foreign key, a content_json field holding the structured output of the AI, a pdf_url, the ai_model_used, and created_at. Saving structured content_json per version allows you to regenerate the PDF later, compare versions, or let the student revert to a previous draft.

Begin by using the ATS-Friendly Technical Resume .tex file as a template with placeholders, e.g., SUMMARY, EDUCATION, and EXPERIENCE. Then write a small templating function, in Python, using string.Template, Jinja2, or a basic string replace, that fills those placeholders from the AI's JSON output. Unescaped characters are a frequent cause of silent compile failure, so escape LaTeX special characters such as &, %, _, #, and $ before inserting any user or AI text. Run the completed template through pdflatex, which requires a LaTeX distribution, like texlive, on the server, or compile it with a hosted compile API should you not wish to deal with that dependency. Lastly, return the compiled PDF to the user, save it on S3 or some other storage, on the local disk, or on Render's disk, and save the reference URL in the ResumeVersion.pdf_url field.

The resume output should remain ATS-friendly, i.e., no pictures, icons, or columns disrupting parsing, standard fonts, reverse-chronological order, and consistent date formats. Reliability is also important: the AI fallback should be silent, so that even with a Grok failure and a Gemini success, the user never sees a raw error. This is a real privacy issue, as the resume content contains actual personal and contact details, and it needs to be treated as PII (i.e., the resume content should not be logged in plaintext, and the database connection should be secured). Performance is also important, since the slow step is the AI generation part; therefore, the application must display a loading state and consider streaming or intermediate updates in case generation takes more than a few seconds.

The app will require the following: a GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET for OAuth, a SECRET_KEY for Flask sessions, a DATABASE_URL pointing to the PostgreSQL instance, a GROK_API_KEY and GEMINI_API_KEY for the AI integrations, and a LATEX_COMPILE_MODE flag set to local or hosted, depending on how PDF compilation is implemented.

During the first two weeks, authentication, the database schema, and a basic intake form will be covered, with no AI yet, just filling a static template. During week three, Grok is integrated to generate content for one hardcoded LaTeX template. Week four entails adding the Gemini fallback and LaTeX escaping, as well as the complete PDF compile pipeline. Week five is focused on resume history and resume versions, as well as edit-and-regenerate on a per-bullet basis. Beyond this, there are stretch goals such as job-description keyword matching and support for multiple resume templates.

There are a few things worth settling before writing code. Is this a team project involving Mohammad, repurposing his existing OAuth and DB infrastructure, or an independent application built from scratch? Does LaTeX compilation need to be self-hosted, or is it possible to run it via a hosted LaTeX-to-PDF API, which is easier to deploy but introduces an external dependency and expense? And should the app support just one template to start, or several?
